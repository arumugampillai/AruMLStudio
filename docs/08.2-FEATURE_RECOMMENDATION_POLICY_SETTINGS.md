## 1. Executive Summary & Core Architectural Invariant

The **Feature Recommendation Policy Settings System** in **AruMLStudio** provides a fully configurable, auditable, and non-destructive management layer for recommendation scoring weights, promotion thresholds, blocking gates, and dataset-context overrides.

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                       CORE DESIGN INVARIANT                                              │
│                                                                                                          │
│                 CHANGING A RECOMMENDATION POLICY MUST NEVER MUTATE HISTORICAL EVIDENCE.                  │
│                                                                                                          │
│  • recommendation_evidence = Immutable historical facts (ground truth validation events)                │
│  • recommendation_policy   = Rules and thresholds used to interpret those facts                          │
│  • feature_context_summary & experimental_lineage_summary = Materialized projections recalculated        │
│    without altering raw evidence                                                                        │
│  • Projections explicitly record: projection_policy_id, projection_policy_version, projection_rebuilt_at │
└──────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

## 2. Policy Settings Architecture & Scope Hierarchy

Rather than treating all settings as global or hardcoding parameters, policies are organized into a tiered scope hierarchy:

```
                          POLICY PARAMETER SCOPE HIERARCHY
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
  GLOBAL INVARIANTS             BOTH (GLOBAL DEFAULT WITH        CONTEXT-SCOPED OVERRIDES
(Fixed Mathematical Bounds)     CONTEXT-SPECIFIC OVERRIDE)        (Market/Horizon Specific)
        │                                │                                │
• min_score (-100.0)             • weight_keep (+25.0)            • promotion_keep_streak
• max_score (+100.0)             • weight_watch (-10.0)           • promotion_min_score
                                 • weight_remove (-35.0)          • remove_block_consecutive
                                 • bonus_consecutive_keep (+15.0) • remove_block_total
                                 • penalty_consecutive_remove     • negative_alert_threshold
```

### 2.1. Disambiguation of Settings
- **`experimental_promotion_min_unique_models`**: Minimum count of distinct models recommending KEEP for `PROMOTION_CANDIDATE` eligibility (Default: `2`).
- **`registry_alert_min_unique_models`**: Minimum count of distinct models agreeing on REMOVE before an `alert` is flagged on a canonical Feature Registry item (Default: `2`).

Implemented in [`apps/chain_replay_ml/production_validation/recommendation_policy.py`](file:///c:/Users/admin/PycharmProjects/AruMLStudio/apps/chain_replay_ml/production_validation/recommendation_policy.py):

class ScoringPolicy:
    weight_keep: float = 25.0
    weight_remove: float = -35.0
    weight_watch: float = -10.0
    bonus_consecutive_keep: float = 15.0
    penalty_consecutive_remove: float = -25.0
    min_score: float = -100.0
    max_score: float = 100.0
    negative_alert_score_threshold: float = -40.0

    remove_block_total_threshold: int = 4
    promotion_candidate_consecutive_keep: int = 3

    registry: FeatureRegistryPolicy = field(default_factory=FeatureRegistryPolicy)

## 4. Policy Versioning, History & Rollback System

Policy history is stored in the `policy_settings_history` table in `feature_recommendation_evidence.db`:

```sql
CREATE TABLE IF NOT EXISTS policy_settings_history (
    history_id INTEGER PRIMARY KEY AUTOINCREMENT,
    policy_id TEXT NOT NULL,
    version INTEGER NOT NULL,
    context_id TEXT,                          -- NULL for global default policy
    settings_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    created_by TEXT NOT NULL DEFAULT 'user',
    change_reason TEXT
);
```

### 4.1. Versioning Semantics
1. **Immutable Historical Versions**: Every save creates a new version increment ($v_1 \to v_2 \to v_3$). Historical versions in SQLite are immutable.
2. **No-Op Save Prevention**: If submitted settings are identical to the active version, the save is a no-op and no duplicate history row is created.
3. **Rollback with Audit**: Rolling back to version $v_k$ copies its configuration into a new active version ($v_{N+1}$) with `change_reason = "Rollback to version vK"`, preserving a forward-only audit log.
4. **Deterministic Projection Sync**: Saving or rolling back automatically triggers `rebuild_all_projections()`, updating `feature_context_summary` and `experimental_lineage_summary` with zero raw evidence mutation.

## 5. Preview Policy Impact (Read-Only Simulation)

Before committing changes to disk, operators can evaluate policy adjustments using **Preview Policy Impact**:
- Computes what score distributions, streak penalties, promotion candidate counts, and candidate blocking states **would look like** under the proposed thresholds.
- Operates entirely in-memory without writing to SQLite or modifying active policy files.

## 7. Policy Parameters vs Query-Time Intelligence Metrics

To avoid architectural confusion, policy parameters are clearly distinguished from Phase 2A and Phase 2B query-time derived intelligence:

```
┌──────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                          POLICY PARAMETERS vs QUERY-TIME INTELLIGENCE                                    │
├─────────────────────────────────────────┬────────────────────────────────────────────────────────────────┤
│ Configurable Policy Settings (Phase 1)  │ • Scoring weights (w_keep, w_remove, w_watch, bonuses)         │
│ (Managed in Tab 5 & Stored in Policy DB)│ • Candidate blocking thresholds (consecutive & total REMOVE)   │
│                                         │ • Promotion candidate criteria (streaks, score, models)        │
│                                         │ • Base Pipeline & Registry alert score thresholds              │
├─────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
│ Query-Time Derived Intelligence         │ • Evidence Confidence C = sqrt(C_runs * C_models) [Phase 2A]   │
│ (Derived at Query Time — NOT in Tab 5)  │ • Model Consensus & Strict Split/Tie Contract [Phase 2A]       │
│                                         │ • Freshness & Staleness Elapsed Age [Phase 2A]                 │
│                                         │ • Operational Priority Score & Advisory Rank [Phase 2A]        │
│                                         │ • Score Volatility σ_S & Trajectory Direction Flips [Phase 2B] │
│                                         │ • Level-1 Cross-Context Generalization Index G [Phase 2B]      │
│                                         │ • Explicit Multi-Dimensional Risk Badges [Phase 2B]            │
└─────────────────────────────────────────┴────────────────────────────────────────────────────────────────┘
```
