## 1. Architectural Purpose & Boundaries

The **Recommendation-to-Training Decision Engine** acts as the deterministic, context-aware policy bridge between historical feature validation evidence and model training.

### 1.1. Core Architectural Question
The Decision Engine answers one specific question:
> **"Given all historical validation evidence, confidence metrics, model consensus, temporal stability, and cross-context generalization for feature $f$ in dataset context $c$, is this feature eligible to enter the Model Builder training candidate set?"**

### 1.2. Separation of Concerns: Implemented Inputs vs Decision Components

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              CURRENT IMPLEMENTED FOUNDATION                            │
├──────────────────────────┬─────────────────────────────────────────────────────────────┤
│ 1. Historical Facts      │ recommendation_evidence (Immutable append-only SQLite log)  │
│ 2. Evidence Projections  │ feature_context_summary, experimental_lineage_summary       │
│ 3. Policy Interpretation │ ScoringPolicy, ExperimentalLifecyclePolicy, BasePolicy      │
│ 4. Evidence Intelligence │ Confidence C, Model Consensus, Freshness, Advisory Rank     │
│ 5. Stability & Context   │ Score Volatility σ_S, Direction Flips, Level-1 Gen Index G  │
├──────────────────────────┼─────────────────────────────────────────────────────────────┤
│                          │             PHASE 3 OPERATIONAL SUBSYSTEMS                  │
├──────────────────────────┼─────────────────────────────────────────────────────────────┤
│ 6. Decision Engine       │ ◄─── IMPLEMENTED (Deterministically derives Training Decs)  │
│ 7. Pre-Training Gate     │ ◄─── IMPLEMENTED (Unifies candidate pruning in Auto Cand)   │
│ 8. Reason Inspector UI   │ ◄─── IMPLEMENTED (Evidence Studio Decision column & dialog) │
│ 9. Model Builder Export  │ ◄─── IMPLEMENTED (Direct export to Feature Selection Presets)│
└──────────────────────────┴─────────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Non-Training Invariant**: The Decision Engine **never** trains models automatically, never modifies feature files on disk, and never triggers background workers without explicit user initiation.

## 3. Context-Scoped Decision Model

### 3.1. Authoritative Decision Key
A training decision is uniquely identified by the tuple:
$$\text{DecisionKey} = (\text{context\_id}, \text{feature\_name}, \text{feature\_source})$$
*(For Experimental features, the lineage key is additionally qualified by $(\text{pipeline\_id}, \text{pipeline\_snapshot\_id})$).*

### 3.2. Why Decisions Must Remain Dataset-Context Scoped
Feature predictive power is fundamentally tied to dataset sampling physics, sliding windows, and market volatility regimes:

```
                          ┌───────────────────────────┐
                          │ Feature: atm_iv_skew_60s  │
                          └─────────────┬─────────────┘
                                        │
           ┌────────────────────────────┼────────────────────────────┐
           ▼                            ▼                            ▼
  Context: NIFTY 3s            Context: NIFTY 15s           Context: SENSEX 1s
  • 5 runs, 3 models           • 2 runs, 1 model            • 3 runs (3 REMOVEs)
  • Score: +85.0 (Fresh)       • Score: +25.0 (Aging)       • Score: -85.0 (Blocked)
  • C = 79.4%, Consensus KEEP  • C = 33.4%, Split Consensus • Context Gate: BLOCKED
           │                            │                            │
           ▼                            ▼                            ▼
   TRAIN_CANDIDATE                   REVIEW                       EXCLUDE
```

1. **Sampling Scale Differences**: A fast microstructure feature may be stable at 3s sampling (`TRAIN_CANDIDATE`), noisy at 15s (`REVIEW`), and non-existent at 60s.
2. **Asset Microstructure Differences**: NIFTY options and SENSEX options exhibit different tick step sizes, liquidity depths, and strike intervals.
3. **No Global Contamination**: An exclusion in SENSEX must **never** block training eligibility in NIFTY.

## 4. The Three Canonical Decisions & The `NEW / UNSEEN` State

The proposed engine evaluates features into three user-facing decisions and one internal pre-training lifecycle classification:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                             CANONICAL DECISION STATES                                  │
├─────────────────┬──────────────────────────────────────────────────────────────────────┤
│ 1. TRAIN_CANDIDATE │ High-confidence, healthy evidence, context CLEAR. Ready for       │
│                 │ Feature Analysis Lab and Model Builder candidate sets.               │
├─────────────────┼──────────────────────────────────────────────────────────────────────┤
│ 2. REVIEW       │ Mixed, aging, or sparse evidence (e.g. SPLIT consensus, Volatile     │
│                 │ σ_S ≥ 35, Stale ≥ 30d, Low Evidence C < 0.30, or Scale-Sensitive).    │
│                 │ Admitted to training candidate pool with explicit review flag.       │
├─────────────────┼──────────────────────────────────────────────────────────────────────┤
│ 3. EXCLUDE      │ Hard exclusion via authoritative Phase 1 rules (Context BLOCKED,     │
│                 │ severe degradation score ≤ -40.0, consecutive REMOVE streak).        │
├─────────────────┼──────────────────────────────────────────────────────────────────────┤
│ * NEW / UNSEEN  │ Internal state for brand-new candidate features with N = 0 runs.     │
│   (Pre-Training)│ Evaluated as NOT BLOCKED → Permitted to enter initial validation.    │
└─────────────────┴──────────────────────────────────────────────────────────────────────┘
```

### 4.1. `NEW / UNSEEN` Feature Lifecycle Handling ($N = 0$)
When Auto Candidate Generation synthesizes a brand-new feature transformation (e.g. `atm_iv_diff_120s`), that feature has zero validation runs ($N = 0$).

```
Brand-New Candidate Feature (N = 0)
        │
        ▼
Is Context BLOCKED in DB?
        ├── YES ──► EXCLUDE (Historically pruned in this context)
        │
        └── NO  ──► Internal: NEW / UNSEEN
                     │
                     ▼
             Pre-Training Elimination Gate: CLEAR
                     │
                     ▼
             Allowed into Feature Transformation Materialization
                     │
                     ▼
             Initial Production Validation Run
                     │
                     ▼
             First Evidence Row Written (N = 1)
                     │
                     ▼
             Decision Engine Evaluates Standard Rules
```

## 5. Separation of Eligibility from Ranking

The platform strictly decouples **Eligibility Determination** (boolean safety gating) from **Candidate Priority Ranking** (sorting for training presets):

```
STEP 1: ELIGIBILITY EVALUATION (Binary Gate)
   Feature f in Context c
        │
        ├── Passes Phase 1 Safety & Gating? ──► NO  ──► EXCLUDE
        │
        ├── Triggers Warning / Scarcity Flag? ──► YES ──► REVIEW
        │
        └── Meets Candidate Thresholds? ───────► YES ──► TRAIN_CANDIDATE

STEP 2: CANDIDATE PRIORITY RANKING (Order of Admitted Features)
   Admitted TRAIN_CANDIDATE & REVIEW Pool
        │
        ├── 1. Experimental PROMOTION_CANDIDATE (Tier 1 Priority)
        ├── 2. Base Pipeline Priority Rank (Phase 1 Default Order)
        ├── 3. Operational Priority Score (Evidence Score × Confidence)
        ├── 4. Advisory Rank (Confidence-Adjusted Order)
        └── 5. Feature Name (Deterministic Alpha Tie-Breaker)
```

> [!TIP]
> **Advisory Rank Invariant**: `advisory_rank` is used strictly as a **sorting criterion** in Model Builder export presets; it **never** determines whether a feature is `TRAIN_CANDIDATE` vs `EXCLUDE`.

## 7. Deterministic Decision Matrix

The Decision Engine executes a three-stage evaluation chain:

```
                              ┌────────────────────────┐
                              │    INPUT FEATURE f     │
                              └───────────┬────────────┘
                                          │
                    ┌─────────────────────▼─────────────────────┐
                    │  STAGE 1: HARD EXCLUSION EVALUATION       │
                    │  • Is Context BLOCKED? (Phase 1)          │
                    │  • Consecutive REMOVEs ≥ 2? (Phase 1)     │
                    │  • Total REMOVEs ≥ 4? (Phase 1)           │
                    │  • Severe Score ≤ -40.0? (Phase 1)        │
                    └─────────────────────┬─────────────────────┘
                                          │
                        ┌─────────────────┴─────────────────┐
                   YES (Any)                               NO (All)
                        │                                   │
                        ▼                                   ▼
                   ┌─────────┐            ┌───────────────────────────────────┐
                   │ EXCLUDE │            │  STAGE 2: REVIEW FLAG EVALUATION  │
                   └─────────┘            │  • Low Evidence Volume (C < 0.30)?│
                                          │  • Dominant Consensus == WATCH?   │
                                          │  • Multi-Model REMOVE Disagreement│
                                          │  • Consensus SPLIT (is_tie=True)? │
                                          │  • Freshness == 'Stale' (≥ 30d)?  │
                                          │  • Volatility σ_S ≥ 35.0?         │
                                          │  • Generalization Scale-Specific? │
                                          │  • Health Status == 'alert'?      │
                                          └─────────────────┬─────────────────┘
                                                            │
                                          ┌─────────────────┴─────────────────┐
                                     YES (Any)                               NO (All)
                                          │                                   │
                                          ▼                                   ▼
                                     ┌─────────┐                     ┌─────────────────┐
                                     │ REVIEW  │                     │ TRAIN_CANDIDATE │
                                     └─────────┘                     └─────────────────┘
```

### 7.1. Rule Group E: Hard Exclusion (`EXCLUDE`)
Governed **strictly by authoritative Phase 1 rules**:
- **E1 (`CONTEXT_BLOCKED`)**: Feature is Experimental and `context_status == "BLOCKED"` `[Inherited Phase 1]`.
- **E2 (`REMOVE_STREAK_EXCEEDED`)**: `consecutive_remove_count >= remove_block_consecutive_threshold` (default: 2 for Experimental) `[Inherited Phase 1]`.
- **E3 (`TOTAL_REMOVE_EXCEEDED`)**: `remove_runs >= remove_block_total_threshold` (default: 4 for Experimental) `[Inherited Phase 1]`.
- **E4 (`SEVERE_DEGRADATION`)**: `evidence_score <= negative_alert_score_threshold` (default: -40.0) `[Inherited Phase 1]`.

> [!IMPORTANT]
> **Consensus Non-Exclusion Principle**: Multi-model disagreement (e.g. `REMOVE + KEEP` split) or multi-model `REMOVE` that has not breached Phase 1 consecutive streak or degradation thresholds is routed to **`REVIEW`**, never hard `EXCLUDE`.

### 7.2. Rule Group R: Review Required (`REVIEW`)
A feature not excluded is assigned `REVIEW` if any warning or evidence-scarcity condition triggers:
- **R1 (`LOW_EVIDENCE`)**: `total_runs >= 1` and `evidence_confidence < 0.30` `[Proposed Phase 3 Parameter]`.
- **R2 (`CONSENSUS_SPLIT`)**: `is_consensus_tie == True` `[Inherited Phase 2A]`.
- **R3 (`DOMINANT_WATCH`)**: `dominant_recommendation == "WATCH"` `[Inherited Phase 2A]`.
- **R4 (`MODEL_DISAGREEMENT_REMOVE`)**: Model consensus dominant recommendation is `REMOVE` without breaching hard Phase 1 exclusion thresholds `[Inherited Phase 2A]`.
- **R5 (`STALE_EVIDENCE`)**: `freshness_label == "Stale"` ($> 30\text{d}$) `[Inherited Phase 2A]`.
- **R6 (`HIGH_VOLATILITY`)**: `score_volatility >= 35.0` with $N \ge 3$ runs (`[UNSTABLE]`) `[Inherited Phase 2B]`.
- **R7 (`SCALE_SPECIFIC_DIVERGENCE`)**: `generalization_label == "Scale-Specific"` ($G < 0.25$) `[Inherited Phase 2B]`.
- **R8 (`HEALTH_ALERT`)**: Feature is in Feature Registry or Base Pipeline with `lifecycle_status == "alert"` `[Inherited Phase 1]`.

### 7.3. Rule Group T: Training Eligibility (`TRAIN_CANDIDATE`)
A feature is assigned `TRAIN_CANDIDATE` if it satisfies all of the following:
- **T1 (`NOT_EXCLUDED_OR_FLAGGED`)**: Neither Group E nor Group R triggered.
- **T2 (`MINIMUM_SCORE`)**: `evidence_score >= training_candidate_min_score` (default: +20.0) `[Proposed Phase 3 Parameter]`.
- **T3 (`CONFIDENCE_SUFFICIENT`)**: `evidence_confidence >= 0.30` `[Proposed Phase 3 Parameter]`.
- **T4 (`DOMINANT_KEEP`)**: `dominant_recommendation == "KEEP"` or zero negative votes `[Inherited Phase 2A]`.

## 8. Safe Integration of Experimental Promotion Candidates

`PROMOTION_CANDIDATE` is an authoritative Phase 1 experimental lineage state evaluated when:
$$\text{consecutive\_keep} \ge 3 \land \text{unique\_models} \ge 2 \land \text{evidence\_score} \ge 75.0 \quad \text{[Inherited Phase 1]}$$

### 8.1. Gated Promotion Candidate Flow
Rather than unconditionally bypassing safety gates, `PROMOTION_CANDIDATE` features pass through standard safety checks:

```
Experimental Feature has PROMOTION_CANDIDATE lineage state
        │
        ▼
Context CLEAR? (Not BLOCKED)
        ├── NO  ──► EXCLUDE
        │
        └── YES ──► No severe degradation (Score > -40.0)?
                     ├── NO  ──► EXCLUDE
                     │
                     └── YES ──► No Stale (≥30d) or Volatile (σ ≥ 35) condition?
                                  ├── NO  ──► REVIEW (Promotion Flagged)
                                  │
                                  └── YES ──► TRAIN_CANDIDATE
                                               (Ranked with Top Priority in Training Presets)
```

## 10. Pre-Training Elimination Gate Unification & Evidence-Driven Parent Ranking

In [`apps/master_dataset_tk/auto_candidate_generation.py`](file:///c:/Users/admin/PycharmProjects/AruMLStudio/apps/master_dataset_tk/auto_candidate_generation.py), candidate generation integrates directly with the Decision Engine through two authoritative mechanisms:

1. **Evidence-Driven Parent Ranking (`rank_features_for_candidate_generation`)**:
   - Exposed via `chain_replay_ml.production_validation.api.rank_features_for_candidate_generation(data_dir_or_conn, features, context, policy)`.
   - Ranks all candidate source features deterministically using Phase 1–3A standing:
     - `is_candidate_generation_allowed` (True before False)
     - `is_training_candidate` (True before False)
     - Decision Priority Tier (`PROMOTION_CANDIDATE_QUALIFIED` > `TRAIN_CANDIDATE` > `NEW_UNSEEN` > `REVIEW` > `EXCLUDE`)
     - `operational_priority_score` (higher evidence scores first)
     - `feature_name` (alphabetical tie-breaker)
   - Consumed by `select_interaction_parent_features()` to allocate a 36-parent budget stratified across canonical Feature Registry domains with deterministic round-robin redistribution.

2. **Pre-Training Elimination Gate (`evaluate_candidate_training_eligibility`)**:
   - Queries the SQLite Evidence DB to evaluate complete decision outcomes for all generated candidate names.

```
Auto Candidate Generation
  │
  ├── 1. Rank Source Features via rank_features_for_candidate_generation(context, features)
  │      └── Select 36 domain-stratified interaction parents (with Commutative Deduplication A ≤ B)
  │
  ├── 2. Generate candidate definitions (lags, differences, interactions)
  │
  ├── 3. Pass candidate names to evaluate_candidate_training_eligibility(context_id, names)
  │      ├── EXCLUDE features ────► Pruned immediately (Blocked from parquet materialization)
  │      ├── NEW / UNSEEN features ► Admitted to initial transformation build (N = 0)
  │      ├── REVIEW features ─────► Admitted with review warning
  │      └── TRAIN_CANDIDATE ─────► Admitted cleanly
  │
  └── 4. Materialize transformations only for non-excluded candidates (Saves CPU/disk)
```

## 16. Comprehensive Test Plan for Phase 3 Implementation

The future test suite (`test_recommendation_to_training_decision_engine.py`) will assert:

1. **`NEW / UNSEEN` Feature Admittance**: $N = 0$ unblocked features are cleared for initial validation.
2. **Context Gating**: Blocked experimental features $\implies$ `EXCLUDE`.
3. **Consensus Non-Exclusion**: Multi-model REMOVE disagreement $\implies$ `REVIEW`, not `EXCLUDE`.
4. **Gated Promotion Candidate**: `promotion_candidate` passes safety gates to achieve top-priority `TRAIN_CANDIDATE`.
5. **Eligibility vs Ranking Decoupling**: Advisory rank does not alter decision state.
6. **Low Confidence Evidence Scarcity**: $C < 0.30 \implies$ `REVIEW` (`LOW_EVIDENCE`), not `EXCLUDE`.
7. **Registry & Base Immunity**: Registry and Base Pipeline features are never auto-blocked.
8. **Consensus Split**: `is_consensus_tie == True` $\implies$ `REVIEW` (`CONSENSUS_SPLIT`).
9. **Volatility Threshold**: $\sigma_S \ge 35.0 \implies$ `REVIEW` (`HIGH_VOLATILITY`).
10. **Timeframe Divergence**: $G < 0.25 \implies$ `REVIEW` (`SCALE_SPECIFIC`).
11. **Zero DB Mutation**: Checksum before and after decision queries is 100% identical.
12. **Model Builder Preset Export**: Generated preset JSON matches eligible feature set.
